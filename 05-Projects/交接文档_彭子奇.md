## 订单系统重构
### 新架构
这部分内容在 `canrd-erp` 的 `docs/ARCHITECTURE_GUIDE.md` 里描述的很详细了，这里我就补充一些题外话

**当前这套架构不是纯血 DDD**
- 纯血的 DDD 是有 application 层的。其作用是用于编排 domain 和 repository 从而实现完整的业务需求，但是由于本套系统要使用工作流来编排业务，所以其实也就替代了 application 层的功能，所以我在设计架构时就把 application 层砍掉了。
- 纯血的 DDD 中 domain 领域之间是不能直接调用的，是要通过领域事件进行通信的，但目前我设计的 domain 之间是直接调用的。因为根据我所学的知识来看，DDD 这么处理是为了微服务做准备，为了将来划分微服务更加便利，我认为我们公司目前的团队规模不太可能把订单系统拆成微服务，而且加上领域事件要引入 redis 或者 kafka 等中间件，增加了系统复杂度，我主观认为没有必要这么干。

### 工作流
这部分内容在 `canrd-erp` 的 `docs/WORKFLOW_GUIDE.md` 里描述的很详细了，这里我就补充一些题外话
- 推荐安装 idea 插件 [LiteFlow-Helper](https://plugins.jetbrains.com/plugin/index?xmlId=com.yomahub.LiteFlow-Helper&utm_source=product&utm_medium=link&utm_campaign=IU&utm_content=2026.1)，可以在右侧窗口快速跳转到对应的节点，还能从对应节点快速跳转到对应的组件
- 我个人认为，如果订单的流程直到目前为止依旧变动频繁，那其实并不适合将其用 xml 重构成工作流。因为如果订单的流程变动频繁，其实每一次的改动成本会比重构之前大很多，不仅要改动 xml 文件，还要考虑改动前后的适配问题
