# 2 订单系统 - 财务应付
## 2.1 风险说明 ⭐
财务应付模块存在一个潜在风险：钉钉接口调用额度可能不足。

当前系统默认通过付费 API 同步钉钉审批数据。若仅线上环境使用，付费 API 每月 5000 次 的调用额度基本能够满足业务需求。但在实际研发过程中，本地开发环境、测试环境通常也需要调用钉钉接口进行联调、功能测试及问题排查，因此整体调用量会明显增加，存在超过付费 API 月度调用额度的风险。

## 2.2 背景信息
**钉钉提供两套独立的数据同步机制**：

|方式|调用额度|数据时效性|
|---|---|---|
|付费 API|5000 次/月|定时轮询，通常存在约 1 天同步延迟|
|Stream 事件推送|3000 次/月|事件实时推送，无同步延迟|

**当前需要同步的钉钉表单**：
- 付款单
- 日常报销
- 付款单（订单系统自动推送）

**当前系统实现情况**：
- 系统已同时实现付费 API 和 Stream 事件推送两套同步方案。目前通过配置项统一切换同步方式，即三个表单只能整体切换，暂不支持按表单分别配置同步方式。
- 为避免非生产环境占用接口额度，application.yml 中默认关闭了 dev、test 环境的数据同步，可根据实际联调需求灵活开启或关闭。

## 2.3 优化建议 ⭐
若后续运行过程中发现付费 API 调用额度不足，建议将同步方式调整为按表单配置，而不是统一切换，使不同表单分别使用不同的同步机制，从而将调用压力分散到两套额度体系，降低单一额度耗尽导致同步异常的风险。

**例如**：
- 付款单：使用 Stream 事件推送；
- 日常报销：继续使用付费 API；
- 付款单（订单系统自动推送）：继续使用付费 API；

# 3 订单系统 - 重构
## 3.1 新架构
这部分内容在 `canrd-erp` 的 `docs/ARCHITECTURE_GUIDE.md` 中已有详细描述，这里仅做一些补充说明。

**当前这套架构并非纯血 DDD**
- 纯血 DDD 会有一个 application 层，其作用是编排 domain 和 repository 来实现完整的业务需求。但由于本系统使用工作流来编排业务，实质上替代了 application 层的功能，因此在设计架构时便将其省略。
- 纯血 DDD 要求各领域之间不能直接调用，而是通过领域事件进行通信。但目前的设计中，domain 之间是直接调用的。据我了解，DDD 这样做主要是为微服务拆分做准备，以便将来更方便地划分微服务。然而以我们公司目前的团队规模，将订单系统拆成微服务的可能性不大；加上引入领域事件需要依赖 Redis 或 Kafka 等中间件，会增加系统复杂度，我认为当前阶段没有必要这样做。

## 3.2 工作流
这部分内容在 `canrd-erp` 的 `docs/WORKFLOW_GUIDE.md` 中已有详细描述，这里仅做一些补充说明。

**个人建议**

## 3.3 数据库
数据库的部分表结构可能存在不够合理的地方，某些字段也可能是冗余或无用的，后续如果需求任务不多的话，可以考虑优化。

## 3.4 重构建议 ⭐
- 目前新架构是按照领域进行划分，所以重构也应该按照业务领域为单位进行重构。
- 重构的顺序，我建议是先重构稳定的模块。因为不稳定的模块本身有缺陷或者变动频繁，如果重构过去排查问题可能不好排查。
- 像是上传文件、记录业务日志、登录，我都抽取到了 `support` 层里，这一块也可以先重构，也就是前端所有调用上传文件、登录的地方都可以改为请求到新后端的这个模块。
- 登录这一块，当时茂哥说要把所以内部系统的登录做成一个服务，我理解就是做一个登录网关。到时候可以直接把 `support` 层里的 `security` 包移出去就好了，很方便。
- 订单相关流程后续肯定要用工作流重构的，但如果目前流程仍在频繁变动，我不建议当下重构。因为 XML 流程变动的成本是要更高的，不仅要修改 XML 文件，还要处理改动前后的适配问题。
- 目前嘉仁是把订单流程拆成了两条：电解液订单流程、非电解液订单流程。我对于业务不算熟悉，这样拆分是否合理我无法判断。电解液订单流程、非电解液订单流程是否流程有重叠？是否还能继续往下拆的更加清楚些？里面是否混杂了其他领域的流程？这些都是需要确认的。
